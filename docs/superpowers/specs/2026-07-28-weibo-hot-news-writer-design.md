# 微博热搜图文改写应用设计

## 目标

交付一个可在本机运行的 Web 应用：用户从微博热搜中选择一至三条娱乐、体育或社会类选题，应用取得可公开访问的原始资讯与图片，生成一篇约 600 字、可追溯来源的原创图文稿。

## 范围与边界

- 热搜来源为微博公开热搜页；页面展示抓取时间、热词热度及原始链接。
- 正文优先使用公开可访问的微博正文及其图片。正文无法公开取得时，使用该热词关联的公开媒体报道。
- 若没有足以支撑成稿的正文，或无法从所采用资讯取得三张清晰图片，则该选题不能生成，界面说明具体原因；不根据标题编造内容，也不生成非来源图片。
- 单次可选择一至三条选题。每条选题各自生成一篇成稿，不混合不同事件的事实和图片。
- 本次不包含登录微博、发布微博、永久保存用户密钥、后台定时抓取或多用户账户。

## 技术方案

采用 Python 3.12、FastAPI、Jinja2、HTTPX、BeautifulSoup、Pillow 与 DashScope SDK。FastAPI 同时提供服务端渲染页面和 JSON 端点，避免引入独立前端工程。

组件职责：

1. `hot_search` 抓取并解析微博公开热搜页，产出标题、排名、热度、链接及可识别的分类信息。界面仅将娱乐、体育、社会类选题呈现为可选项。
2. `source_resolver` 依次尝试公开微博正文，再检索关联公开报道，提取正文、标题、发布日期、来源 URL 和正文图片。对每个来源记录提取失败原因。
3. `writer` 将已验证事实、类别和背景线索发给 DashScope，要求生成六个段落、总字数 550–650 字、每段不超过 150 字的中文稿。
4. `image_processor` 仅处理已采集的资讯图：以主体居中的 16:9 裁剪、轻度亮度/对比度/色温调整，并输出独立图片文件。
5. `exporter` 将六段正文、每两段后的处理图、原始来源和抓取时间组合为页面、Markdown 复制内容及可下载的独立 HTML。

## 用户流程

1. 打开本地首页，点击“刷新热搜”。
2. 在娱乐、体育、社会筛选中查看并勾选一至三条热搜。
3. 可选地在界面输入本次使用的 DashScope API Key；服务端优先读取 `.env` 的 `DASHSCOPE_API_KEY`，临时输入仅保存在当前请求内存。
4. 点击“生成图文”。应用为每条选题解析来源和素材，再生成成稿。
5. 结果页展示文章、三张处理图、所有实际采用来源与失败原因；用户可复制 Markdown 或下载独立 HTML。

## 内容生成要求

- 不改变原始资讯的核心事实；只允许以来源明确支持的内容补充事件前因、公开背景或相似案例。
- 使用自然、流畅的中文重写，不连续复用原文句子；提示词目标原创表达比例不低于 80%。
- 固定输出六段正文。每段不超过 150 字，总长 550–650 字；图片分别置于第 2、4、6 段之后。
- 文章保持积极、克制的表达，兼顾读者视角；末段给出与事件相关、非煽动性的讨论切口。
- 去除 AI 味：禁用“值得一提的是”“不难发现”“在这个信息爆炸的时代”等模板句，避免空泛升华、机械排比、重复句式和无依据的情绪判断；保留具体人物、时间、行动和可验证细节。生成后执行一次规则化风格检查，不通过则用同一来源重写一次。
- 生成失败或风格检查仍不通过时，不输出不合格成稿，并给出可操作的错误提示。

## 错误处理与合规

- 网络超时、微博页面结构变化、访问限制、正文不足、图片不足、DashScope 失败和无效 API Key 均以界面可读错误返回。
- 输出始终附带来源标题、URL 和抓取时间；不隐藏正文回退事实。
- 仅在本地按用户操作抓取公开页面；不绕过登录、验证码、访问限制或付费墙。

## 测试与验收

- 热搜解析、类别过滤、来源回退、成稿格式与风格检查、图片裁剪滤镜、HTML 排版各有自动化测试。
- 以固定 HTML 和图片 fixture 测试抓取与处理，不在测试中请求微博、媒体网站或 DashScope。
- 启动后可在浏览器完成“刷新热搜 → 选择选题 → 输入/读取密钥 → 生成 → 查看来源与三图 → 下载 HTML”的流程。
- 生成结果满足六段、550–650 字、每段不超过 150 字、每两段一张处理图、三张图均来自所采用资讯、来源可追溯。
